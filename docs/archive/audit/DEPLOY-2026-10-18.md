# Live deploy: audit fixes (18 October 2026)

This runbook covers every change since the Stage 1 audit, except the loan calculation logic, which was deliberately left untouched. Each module file in `modules/` has a "Fixes applied (2026-10-18)" section with the details.

All SQL scripts are safe to run more than once and work on MariaDB 10.3. All nine were tested twice on a copy of `loans_main`. The schema they produce matches `php artisan migrate` exactly, and no migration row is duplicated.

## 1. Before you start
```bash
mysqldump --single-transaction --routines --triggers <db> > backup_$(date +%F).sql
tar czf storage_public_$(date +%F).tgz storage/app/public
```

## 3. Code and caches
Run `npm run build` locally, upload the code and `public/build`, then:
```bash
php artisan permission:cache-reset && php artisan optimize:clear
```
Check that `APP_DEBUG=false` and that the mail settings are correct. Check that `mysqldump` is available and `proc_open` is allowed, otherwise the admin backup button won't work.

```bash
php artisan roles:sync --dry-run && php artisan roles:sync                  # mirror: 5 borrowers given a Spatie role, 0 conflicts

php artisan investments:fix-house-funding --dry-run && php artisan investments:fix-house-funding   # house funding #1 committed and drawn set to 186,000
```

`wallets:check --repair-partners` is safe now: it refuses to run while any journal row points at the wrong wallet. You shouldn't need it.

## 5. Loan statuses and the scheduler
```bash
php artisan loans:update-statuses --dry-run
php artisan loans:detect-npl --dry-run
```
On the mirror, the first real run changes 19 loans: 11 become **defaulted**, and each gets a recovery case; 8 become **overdue**. Check loans **#177, #200, #208 and #217** by hand first, because they may be repaid loans with an out-of-date status. Then run both commands without `--dry-run`, and add this cron job in CyberPanel:
```
* * * * * cd /home/<site>/public_html && php artisan schedule:run >> /dev/null 2>&1
```
`php artisan schedule:list` should show both jobs, at 01:00 and 01:30 Nairobi time.

**Never run `loans:repair-cycles` on live.** It crashes on its own; the work is rolled back, but it is broken.

## 6. Quick checks after deploying
- `/storage/agreements/...` and KYC file URLs return 404. The borrower and staff can still open them inside the app.
- A wrong URL shows the branded 404 page.
- An auditor gets 403 when trying to create a user or a disbursement.
- `/audit-log` shows new rows after you edit a loan.

## Still open: decisions needed (see AUDIT.md §5)
- **Loan calculation:** penalty, rollover, how "repaid" is decided and what `loans.amount` means. A recovery collection can mark a loan repaid while the case still shows debt, because of the unchanged "repaid" rule.
- **Six-account repayment split and history restatement:** which broker rate applies and how penalties are split.
- **References `TO BE PAID`, `BROKER FEE(S)` and `SPLIT`:** cash or not.
- **"Mark as recovered" on a case** still sets the loan to repaid with no money posted.
- **Repayment edit and delete** still require the admin or broker role as well as the permission. Relaxing this needs your approval.
- **Email verification enforcement, the penalty clause wording, KRA PIN uniqueness, credit bureau checks, the paybill shown to customers, and the limit floor.**
